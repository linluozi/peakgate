# peakgate

一个零依赖的 Python「每次调用峰值分配」测量器与 A/B 门禁：每次调用都从自己的
高水位起算，用 `tracemalloc` 给出**可复跑的峰值字节数**，并同时给出时间轴，让你
看清「省内存」是否以变慢为代价。

`Upstream: none` —— 本仓库是原创测量工具，不修改、不 fork 任何上游库。

## 为什么需要它

内存回归通常比速度回归更隐蔽：时间轴在同一台机器上的相对标准差常见 1%–8%，
要用几十到几百次采样才能分辨 2% 的差异；而每次调用的峰值分配量在 40 次采样里
只出现 2–3 个不同值（差别来自测量调用自身分配的 32–56 字节）。这意味着**几次
采样（而不是上百次）就能分辨 2% 的分配差异**，而不必和机器噪声搏斗。

本仓库把这件事做成可复跑的证据，而不是一句经验：

| 轴 | 40 次采样的不同值 | 相对标准差 | A/A 1% 预算假阳性（30 组 × 3 次） |
| --- | --- | --- | --- |
| 峰值分配（本工具） | 2–3 个，spread 32–47 B | 1.8e-6 – 2.3e-3 | **0 / 30** |
| 墙钟时间 | 40 个（全不同） | 1.3e-2 – 3.2e-2 | **24 / 30** |

A/A 指两臂跑完全相同的函数；任何「回归」都是假阳性。时间轴在 1% 预算下
30 组里有 24 组误报（比值范围 0.950–1.424），分配轴 0 组误报（比值恒为 1.000）。

## 真实语料上的一个可执行结论

在 1,000,000 字符的**真实 CPython 标准库源码**（sha256 见
`evidence/summary.json`）上匹配 84,325 个标识符：

| 写法 | 峰值分配 | 墙钟中位 | 峰值比 | 时间比 |
| --- | --- | --- | --- | --- |
| `re.findall(...)` 一次物化全部匹配 | 4,711,323 B | 85.73 ms | 1.0 | 1.0 |
| `re.finditer(...)` 流式消费 | 2,229 B | 87.03 ms | **0.000473（低 2,113×）** | 1.015（慢 1.5%） |

结论：`finditer` 用 1.5% 的时间换掉了 99.95% 的峰值分配。这个权衡用时间轴几乎
看不见（1.5% 落在噪声里），用分配轴 5 次采样就能判定。

2% 合成对照（1,000,000 vs 1,020,000 个 int）：分配轴测得比值 **1.01999938**，
5 次采样即判定；同一对函数的时间轴相对标准差 7.7%，按正态近似要 **114 次**
采样才能分辨 2%。

## 安装与运行

```bash
python3 -m venv .venv && .venv/bin/pip install -e . pytest
.venv/bin/python -m pytest tests -q
.venv/bin/python evidence/run_evidence.py
```

第一条命令即可跑测试；第二条重跑全部证据（约 15 秒，写出
`evidence/summary.json` 与 `evidence/raw/*.json`）。

CLI：

```bash
.venv/bin/python -m peakgate measure your_module:your_function --reps 31
.venv/bin/python -m peakgate compare your_module:old your_module:new --peak-budget 0.01
```

`compare` 在任一轴超过预算时退出码为 1，可直接当 CI 门禁用。

## 独立复跑（干净 clone）

同一台机器、同一解释器，在全新 clone 中重跑
`.venv/bin/python evidence/run_evidence.py`（13.3 s）：

| 指标 | 首次运行 | 干净 clone 复跑 |
| --- | --- | --- |
| 真实语料峰值比 | 0.00047311551341311137 | **0.00047311551341311137（15 位完全相同）** |
| 真实语料时间比 | 1.015 | **0.985（符号翻转）** |
| A/A 分配轴假阳性 | 0 / 30 | **0 / 30** |
| A/A 时间轴假阳性 | 24 / 30 | **13 / 30** |

分配轴的比值可以逐位复现；时间轴的比值连方向都不稳定。原始数字见
`evidence/clean_clone_repro.json`。

## 本轮创新

首次把「每次调用的 `tracemalloc` 峰值增量」做成带**确定性证书**的 CI 门禁，并
在同一批 A/A 语料上量化它与时间轴的检测下限差距：40 次采样仅 2–3 个不同值、
A/A 1% 预算 0/30 假阳性，而时间轴 24/30；真实 1 MB 源码上 `findall`→`finditer`
把峰值从 4.71 MB 降到 2.23 kB（2,113×）而只慢 1.5%。与台账里的 `speedgap`
（合成 vs 真实时间轴）、`benchreconcile`（声明对账）、`coldbudget`（冷启动时间轴）
不同，这条轴测的是**分配量而非时间**，且给出的是可复跑的字节数。

## 限制（必须读）

- `tracemalloc` 只统计 Python 层分配（PyMem），**看不到** NumPy/ORJSON 等 C 扩展
  直接 `malloc` 的缓冲区；对这些库本工具会低估峰值。
- 追踪是进程级的：测量期间不要有其他线程分配；本工具不做线程隔离。
- 开启追踪会明显拖慢被测代码：本机 1 MB `findall` 实测 27.68 ms（未追踪）→
  89.87 ms（追踪），**3.25×**（`evidence/tracing_overhead.json`）；时间数字只用于
  同一次测量内的相对比较。
- 峰值包含返回值本身；返回大对象的函数，峰值反映的是「调用 + 返回值」。
- 每次采样前执行 `gc.collect()`；关掉它（`collect=False`）会改变数字。
- 极小峰值（如 2 kB）上，测量自身的 32–47 B 会带来 1%–2% 的相对抖动，
  `finditer` 的 2.3e-3 rel_sd 就是这个原因，不是被测代码不稳定。

## 环境

- AMD EPYC 7K62 4 vCPU / 3,723 MiB RAM / Linux 6.8.0-124-generic
- CPython 3.12.3；本机只有 3.12，未做跨版本交叉
- 依赖：仅标准库；测试用 pytest
- 证据：`evidence/summary.json`、`evidence/clean_clone_repro.json`、
  `evidence/tracing_overhead.json` + `evidence/raw/` 下 35 个原始样本文件
- 语料：`sysconfig.get_paths()["stdlib"]` 下按文件名排序的 `*.py`，截取
  1,000,000 字符；文件数与 sha256 记录在 `evidence/summary.json`
